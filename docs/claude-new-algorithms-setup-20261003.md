Written by Claude. Follows `docs/claude-new-algorithms-20261002.md` (the decision to add
cuVSLAM, SVO Pro, MASt3R-Fusion and DSOL). This file says what is installed, how each
algorithm is configured, what the first pilot runs gave, and what is still open.

**Where:** everything is in a separate checkout, `/data/imoroz/vslam-benchmark-newalgos`,
branch `new-algorithms` (off `3cee23b`). Nothing is committed and the main checkout was not
touched. Datasets are links into the main checkout.

**Status in one line:** all four algorithms are installed, run end to end through runners
of the usual form, and are registered in main's evaluation, campaign and reporting tools
(branch `new-algorithms`, not yet merged into main). No N=3 run exists and the GNSS run
types are not wired up.

## 2. How the parameters were chosen

### One calibration source for all four

`configs/sensors/<dataset>.json` holds, per dataset, the camera model, stereo baseline,
camera–IMU transform, IMU noise and camera–IMU time offset. It is generated by
`scripts/setup/build_sensor_profiles.py` from the configs the benchmark already runs
(ORB-SLAM3 stereo-inertial config for geometry and IMU noise, Basalt calibration for the
time offset). `--check` compares the result with the OKVIS2 and Basalt configs of the same
dataset and fails on disagreement; every new runner calls it before it starts.
All four algorithms get their calibration written from this profile at run time, so they
cannot drift apart or away from the existing rows.

| Dataset | Image | Baseline | Camera–IMU lever | Time offset | Input |
|---|---|---|---|---|---|
| EuRoC | 752×480, 20 Hz | 0.1101 m | 68.9 mm | 0 | raw + distortion model |
| Rosario v2 | 1280×720, 15 Hz | 0.0497 m | 33.9 mm | 0 | pre-rectified |
| HortiMulti | 640×480, 10 Hz | 0.1395 m | 139.2 mm | 9.16 ms | pre-rectified |
| ZED2i | 1920×1080, 10 Hz | 0.1198 m | 23.1 mm | 0 | pre-rectified |

The time offset is applied the way the repaired Basalt runner does it: IMU timestamps are
moved onto the camera clock before the estimator sees them, and the estimator's own offset
parameter stays zero.

### Estimator settings

One settings file per algorithm, the same for every dataset. Nothing was tuned on results.

| Algorithm | Base | What the benchmark changes |
|---|---|---|
| cuVSLAM | library defaults | bundle adjustment and loop closing run inside the tracking call instead of background threads, so the result does not depend on how fast frames are fed |
| SVO Pro | upstream `vio_stereo.yaml` | back-end time limit removed (as in the authors' offline benchmark files); five settings upstream marks as "increase for larger images" are scaled with image width; VO switches the IMU, back end and loop closing off |
| MASt3R-Fusion | upstream `base_euroc.yaml` | frame subsampling so the processing rate is 10–15 Hz (the authors run at 10 Hz); nothing else |
| DSOL | upstream `dsol.yaml` + upstream TartanAir override | nothing |

IMU noise:

| Algorithm | EuRoC | Rosario, HortiMulti, ZED |
|---|---|---|
| cuVSLAM | sensor profile | sensor profile |
| SVO Pro | authors' own EuRoC values | the benchmark's OKVIS2 values (same back-end formulation and parameter meaning) |
| MASt3R-Fusion | authors' own EuRoC values | sensor profile |

"Sensor profile" means the ORB-SLAM3 values: calibration values for EuRoC, Rosario and
HortiMulti, the shared field profile for ZED.

### How each one is driven

- **cuVSLAM** – own driver (`scripts/run/_cuvslam_track.py`) around the Python API, modelled
  on the upstream EuRoC example. With loop closure the exported trajectory is the one
  recomputed from the final pose graph; without it, the per-frame odometry.
- **SVO Pro** – the authors' offline benchmark node (`svo_benchmark`), not the live ROS node.
  It reads images and IMU from disk and waits for the back end after each frame. The exported
  trajectory is the node's real-time estimate in every run type. With loop closing on, loop
  corrections are fed back into the estimator, but earlier poses are not rewritten (the
  pose-graph file it also writes has keyframes only, about one pose per 20–30 frames).
- **MASt3R-Fusion** – the authors' three scripts. VIO is the real-time stage; VIO-LC adds
  loop detection and global optimisation and exports the globally optimised trajectory,
  which has keyframes only (129 poses for MH_01, 849 for Rosario seq1).
- **DSOL** – the authors' offline node with its generic stereo-folder reader. That reader
  has no ground-truth input (the earlier note that the offline node "reads ground-truth
  poses" applies to the KITTI/TartanAir readers, which are not used). Raw EuRoC images are
  rectified beforehand from the sensor profile; the other datasets are used as they are.

What the numbers say:

- **cuVSLAM** works everywhere. Visual-only is strong (best VO on Rosario, close to the best
  on ZED). Its inertial mode is worse than its own visual-only mode on Rosario, ZED and
  MH_05. Three repeats on MH_01 and MH_05 agree to within about a centimetre. One run takes
  seconds to three minutes.
- **SVO Pro** with the back end (VIO, VIO-LC) is good on all four datasets, and its Rosario
  VIO is at the level of the best existing VIO row. Its front end alone (VO) loses scale on
  HortiMulti and Rosario.
- **DSOL** works on EuRoC, Rosario and ZED and fails on HortiMulti: in several stretches of
  the run it reports almost no motion while the robot drives on (path length 4–10 % of the
  true one in those stretches).
- **MASt3R-Fusion** runs, but the single-camera scale is wrong on the ground-vehicle data:
  estimated scale 1.34 on HortiMulti and 0.5 on Rosario (EuRoC: 1.02). MH_01 gives the same
  0.363 m with the authors' untouched configuration, so this is not a setup difference.

The three failure cases (bold) look like properties of the methods, not setup faults: the
same setup works on the other datasets, and calibration comes from the same profile. They
are still single runs.

## 4. Decisions

Answered by the user on 3 October 2026:

1. Failed cells stay in the tables as measured failures, provided the setup is correct.
2. cuVSLAM IMU noise: the sensor-profile values (the calibration values every other
   consumer of the profile uses, not tuned on results).
3. Both VIO-LC kinds are reported, each with a note on what the trajectory is.
4. VIO and VIO-LC stay separate executions.

The questions as they were put:


1. **Rows that fail.** Keep SVO Pro VO, DSOL on HortiMulti and MASt3R-Fusion on the field
   datasets as measured failures in the tables, or drop those cells? My suggestion: keep them;
   they are results about the method families.
2. **IMU noise for cuVSLAM on Rosario and HortiMulti.** I used the calibration values from the
   sensor profile. With the benchmark's OKVIS2 values instead, Rosario VIO improves (10.3 →
   7.2 m) and HortiMulti gets worse (0.74 → 0.90 m). There is no principled winner; the
   profile values are the consistent choice unless you prefer otherwise.
3. **SVO Pro VIO-LC and MASt3R-Fusion VIO-LC trajectories** differ in kind from each other and
   from the existing LC rows (real-time estimate vs keyframe-only global optimisation). Fine to
   report as is with a note, or should SVO Pro VIO-LC be left out because it is not a
   retroactively corrected trajectory?
4. **MASt3R-Fusion run cost.** VIO and VIO-LC are separate executions (about 2.5 min for
   MH_01, 21 min for Rosario seq1, an estimated 1.5–2 h for ZED). Sharing one real-time stage
   between the two rows would halve that but ties two rows to one execution.

## 6. Things to know before production

- **Do not edit `scripts/` or `configs/` while a run is in progress.** The provenance check
  rejects the run ("source file membership changed"). I lost one pilot this way.
- **SVO Pro trims inertial runs** to the frames that have IMU samples before and after them
  (HortiMulti: IMU starts 0.1 s after the camera; ZED: IMU ends before the last image). The
  authors' offline node otherwise waits forever on such a frame. The runner also has a
  six-hour limit for the same reason. SVO Pro's exported trajectory starts a few seconds
  into each sequence (95–99 % time coverage) because the node only writes poses once its
  keyframe window is full.
- **MASt3R-Fusion needs matplotlib below 3.9** (the global stage otherwise ends with an error
  after writing its result). The setup script pins it.
- **Unexplained:** twice, the input-hashing step of the shared runner helpers crashed
  (segmentation fault in `_capture_inputs.py`, ZED sequence, five minutes apart). It did not
  recur in later attempts, including one with the same order of runs.
- Six pilot attempts failed for reasons that are not results and are kept as failed attempts
  in the clone's `results/` tree: cuVSLAM Rosario `vio-lc/run1` (I added a file under
  `scripts/` during the run), SVO Pro ZED `vio/run1` (hung at the last frame before the
  trimming fix), SVO Pro ZED `vio/run2` and `vio-lc/run1` (the crash above), MASt3R-Fusion
  MH_01 `vio-lc/run1` (matplotlib, before the pin) and str03 `vio/run1` (started while I was
  changing the environment). Each has a later successful attempt.
- Scratch files are in `results/_pilot/`. Docker images: `vslam_dsol:noetic`,
  `vslam_svo_pro:noetic`. Conda environments: `cuvslam`, `mast3r_fusion`.
- A consistency test for the new calibration paths is in
  `scripts/campaign/tests/test_new_algorithm_calibration.py` (9 tests, passing).
